## T08 开发规则

- 范围：选择已有合成患者的既有就诊，登记申请草稿、查询、编辑草稿、提交。不得自动建患者、并档、换患者或签发报告。首次登记绑定的 scope/患者/就诊/来源不允许后续更换。
- 开发作用域为管理员预配置的医院+院区+科室+来源，使用独立 workflow_scope；它独立于病例，故无病例申请也可授权。来源/科室须同医院、院区与科室具有效关联。作用域身份不可变，失效可禁用。
- 显式 workflow_grant 按 user+scope 授予 READ、WRITE（登记/编辑/提交）；有效期、撤销和 enabled 逐次验证。WRITE 必须有 READ。病例角色、系统管理员、登录本身不产生申请权限。授权不由客户端角色或科室文字推断。
- 只支持服务端标记 synthetic_only 的账号；功能开关默认关闭，仅 dev/test 可启用。生产不得启用此开发工作流。迁移不预置医院、作用域、账号或授权；测试种子只在测试 classpath。
- 身份查询要求显式作用域和精确就诊号，最多返回 20 条，同院且就诊科室必须等于作用域科室。无结果不自动建患者。患者的显示姓名和就诊号由服务端读取，表单不提交患者姓名作为身份。
- 申请内部 UUID 与申请号分离。开发号固定 `DEV-AP-<完整UUID>`，在现有医院/来源唯一域中受 UNIQUE 保护，不代表医院编号标准，无连续无间隙承诺。生成和幂等回执同事务，重放不重新生成。
- 状态 DRAFT→SUBMITTED；仅 DRAFT 可编辑。旧数据没有 workflow 记录，不自动迁移为草稿或已提交，不暴露到新接口。提交后的修改需后续更正流程，本版拒绝。
- 草稿保存临床病史（0–4000 UTF-16 单位）、采样时间（可空 Instant）、业务类型（本版仅开发常规组织类型 ROUTINE）、容器清单（1–20，数量 1–999，部位1–255，侧别 NONE/LEFT/RIGHT/BILATERAL/UNKNOWN；固定液0–128，固定开始时间可空）。此为技术输入边界，不是临床阈值。
- 容器由服务端分配 UUID，创建时逐项建立 specimen_container 及详情。草稿编辑只改原清单的描述，不换容器 ID/数量条目；新增、移除、拆分/合并清单留后续版本，UI 明示该限制。材料数量字段可在草稿修改，接收后不可覆盖。
- 提交要求非空病史、采样时间、各容器固定液和固定时间；固定时间不能早于采样，不强制固定时长。只适用于该开发常规类型，其他病种/材料不支持。未满足返回具体业务拒绝，不自动补时间/固定液。
- 重复识别仅同一授权作用域内同一就诊存在另一份 SUBMITTED 开发申请，不使用临床时间阈值或部位推断，也不泄漏其他不可见作用域的申请。作用域的医院/院区/科室/来源组合唯一。提交失败返回 DUPLICATE_REVIEW_REQUIRED；本版不提供理由绕过，保持 fail-closed。跨来源重复检测及医院复核授权留待批准，不声称本版能排除全部临床重复。
- 列表仅当前授权范围，固定 created_at DESC、id DESC，每页20条，页数1–10000；过滤精确申请号/就诊号、状态和 UTC 申请日期。时间显示明确 UTC，不隐式采用浏览器时区。

## T09 开发规则

- 在 T08 提交申请上接收，不对 DRAFT 或无工作流旧申请操作。接收授权独立 RECEIVE，异常处理独立 EXCEPTION；不因 WRITE 自动获得接收权限。
- 核对输入为精确患者 ID、就诊号和逐个容器 UUID；服务端校验同申请归属、无重复、与计划清单集合一致。人工核对布尔值不替代这些关系校验。身份不符阻断，不可条件放行；数量不符转异常，不自动补容器。
- 接收核对不符时，RECEIVE 权限可原子记录自动 IDENTITY/QUANTITY 异常，返回已确认回执但状态为 EXCEPTION，不能在 UI 声称接收成功；人工登记/恢复/退回仍要求独立 EXCEPTION 权限。禁止静默扫描去重；重扫同一容器造成集合/数量不符。
- SUBMITTED→RECEIVED，创建一个开发病例、权威病例范围与开发病理号 `DEV-P-<完整UUID>`，容器关联该病例及接收时间；病理号/病例/容器/状态/审计/回执原子提交。不得生成重复病例或覆盖原病例。
- SUBMITTED→EXCEPTION，记录类别 IDENTITY/QUANTITY/INFORMATION、本版按整份申请记录异常（不支持单容器处置）、事实说明、创建人/时间；保留追加事件。EXCEPTION→RETURNED 记录退回原因；EXCEPTION→SUBMITTED 仅 INFORMATION 且明确补充说明，恢复时复用 T08 就诊锁和同范围重复提交检查，重新核对后再接收。IDENTITY/QUANTITY 不允许软件自行纠正并恢复，保持阻断。
- 不提供有条件接收、不关闭历史异常、不删除申请、不处理临床身份更正、拒收实物交接设备或打印机。页面禁用这些未实现操作并说明原因。软件退回记录不宣称实物已交接。

## 一致性与技术契约

- Cookie/CSRF、ProblemDetail/trace 和 T07 IdempotentCommands 保持。写请求要求 Idempotency-Key；编辑/提交/接收/异常操作包含 expectedVersion。全部有意义输入进入摘要，重放重新验证确切资源权限，状态/版本前置条件只在首次 mutate 校验。
- 同库业务、成功审计和回执原子提交。顺序锁：当前 app_user SHARE → workflow_scope SHARE → 当前 grant SHARE → 申请 FOR UPDATE → 必要就诊/关联行。锁后重新查当前有效性；撤权 UPDATE、账号停用、scope 禁用与这些锁协调。锁等待后必须重新鉴权，权限时间窗口在实际操作时再检查。禁止先授权后无条件更新。
- 对同一就诊的提交先锁就诊行，再查询其他 SUBMITTED 申请，避免并发重复提交绕过；所有提交遵循相同顺序。过期版本及不合法状态为409，参数400，无权限403，不可见详情404，依赖失败503；数据库未知错误不伪装业务冲突。
- 请求身份不入 URL 或 localStorage；业务草稿只在内存，离开/返回/关闭/退出提示，登录失效立即清除。成功必须以服务器回执和重新读取为准；网络结果未知保留相同 key/输入，先确认或重试相同意图，不允许编辑后复用旧 key。
- 单独新增 T08/T09 迁移，不改 V1–V4；测试覆盖空库、V4升级、旧记录不被自动批准、复合 FK、双连接竞争/撤权、回滚、同键异参、跨范围读取及 HTTP/浏览器闭环。

## 验收与投产阻断

T08：真实登录后有权账号精确查就诊→登记→查询→编辑→提交；无授权/跨范围拒绝，重复提交一次成功，无服务器成功不得假保存。T09：真实提交申请→核对→接收，及异常→补充/退回；身份/数量错配不能成功，历史不覆盖。各项完成后独立提交并核验 CI，不部署。

投产前必须替换或批准：开发开关、合成账号限定、作用域/资格配置、患者主索引、医院编号、病种/材料及固定信息规则、重复申请策略、身份更正、条件接收、实物交接、审计留存和岗位分离。上述未知项不会通过默认允许进入生产。
