## 根因与契约核查

ReviewForm当前对任何不同动作都调用setNext，**空表单也要求动作确认**。不能把CI中没有对话框解释为正常clean分支，不能通过可选点击绕过。成功命令在sendReview读取响应体并校验回执后，由Diagnosis.onSaved递增revision、重挂载编辑器，并重新GET复核详情/历史；外层放弃输入并刷新也重挂载编辑器。仅POST响应头或单个状态文本出现，不代表这些异步步骤及前一个Modal关闭都已完成。

旧act仅检查waitForResponse的status，随后可开始下一动作；刷新路径没有绑定确切GET响应、流程版本和报告修订，也没有等待前一个对话框退出。确切缺陷是测试缺少服务端响应完成→最新版本呈现→干净表单/无残留弹窗的同步契约。同样helper复制于amendment、review、output、delivery四个E2E文件。本地未重放CI真实服务失败时序，不能声称仅凭源码已经证明CI中的每一个事件顺序；新增受控延迟回归用于验证修复的同步约束。没有证据支持删除或改变产品确认门禁，本次不改产品、权限、后端或迁移。

## 修复与确定性回归

四个场景共用review-actions.ts：

- 预先监听对应病例的GET，等待response.finished及完整解析，校验UI精确流程版本、状态、报告修订；等待查询结束、Modal消失，断言病例核对/原因字段为空。
- 预期作者职责分离409时，等待完整错误体并明确断言REPORT_SEPARATION_REQUIRED、对应错误文案、解锁状态和保留原因。没有接受任意错误。
- dirty刷新明确确认放弃，等待此次响应对应的全新表单。动作切换先明确写入未保存原因，再断言清除确认对话框及清除结果；模拟签署仍必须单独确认。
- 成功命令必须等新GET及UI提交完成才返回；不使用sleep、重试、可选点击、吞异常、放宽超时或全套串行化。

UI增加两项确定性回归，使用与E2E同一helper。第一项以POST和随后的GET两道Promise屏障验证：延迟POST时点击动作选择显示区仍不能打开选项/确认框；POST完成但GET尚未释放时helper不能返回，旧表单已卸载；新确切版本加载后clean动作切换仍需确认且可取消，随后dirty切换明确清除并再次确认合成签署。核验提交采用新expectedVersion、确切revisionId及simulationAcknowledged，最终字段为空且冻结。第二项直接复现CI场景的准备路径：作者409拒绝→外部独立复核已提交→dirty刷新明确放弃→延迟新GET→等待父Modal关闭及最新修订→明确动作与模拟双确认，最终仅发送一个绑定新版本的模拟请求。原有未知请求原键重试、409保留输入、取消模拟、病例迟到响应回归完整保留。
